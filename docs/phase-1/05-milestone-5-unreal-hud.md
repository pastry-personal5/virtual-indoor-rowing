# Phase 1 Milestone 5: Unreal integration and live HUD (simulator-driven)

## Relationship to the delivery plan

This is the fifth milestone scoped under [delivery Phase 1](../architecture/10-delivery-plan.md#phase-1--walking-skeleton-46-weeks), per the [Phase 1 packet](README.md)'s "milestones are scoped one at a time" rule. It covers the first part of build-order step 5 ("Minimal Unreal HUD, boat distance-to-spline, stroke animation states"): the Unreal integration seam and the FR-003 live HUD, driven by the PM simulator. The gray-box route, boat distance-to-spline, damped presented distance, and stroke animation states are a later milestone. Real CoreBluetooth wiring, the PM5 picker, and journaling in the app are a separate follow-up milestone (see "Owner-confirmed scoping decisions").

[Milestone 4](04-milestone-4-workout-runtime.md) built `WorkoutRuntime` so that the Unreal work "becomes a thin view over a tested snapshot API". This milestone is the first consumer of that API from Unreal, and the first Unreal product code in the repository: today `VirtualRowing` (`Source/VirtualRowing`) is the Phase 0 diagnostic host with no gameplay, and UBT compiles none of the engine-independent modules — `RowingCore`, `RowingDevice`, `LocalData`, `WorkoutRuntime`, and `RowingContracts` are CMake-only, and the `Concept2PM` plugin's UBT module (`Concept2PMUnreal`) is an empty shell whose real code (`Concept2PMCore`, `Concept2PMMac`) is also CMake-only. Making the engine-independent modules usable from an Unreal module — including a self-contained protobuf — is the highest-risk unknown in build-order step 5, so this milestone isolates it from presentation work and from real-device behavior.

The architecture this implements: `UWorkoutSubsystem` and the game-thread snapshot consumption in [the macOS/Unreal client architecture](../architecture/03-macos-unreal-client.md) ("Runtime subsystems", "Thread and queue model", "UI under exertion"). Requirements touched: FR-003 (live rowing HUD, on simulator data) and FR-004 (Just Row without an account or network, minus route selection). FR-002 (real discovery/selection) and FR-007 (journal) are not exercised through the Unreal app by this milestone; FR-007 was delivered by Milestones 3 and 4 and is exercised in the app by the follow-up.

## Owner-confirmed scoping decisions (2026-09-19)

- **Cut.** Milestone 5 is simulator-driven Unreal integration and the live HUD only. Route, boat distance-to-spline, `presented_distance` damping, `CourseRuntime`, and stroke animation are a later milestone.
- **Real device split out.** Real CoreBluetooth wiring, the PM5 picker, the `NSBluetoothAlwaysUsageDescription` text change, and Keychain-sealed journaling in the app are not in this milestone; they form a dedicated follow-up milestone that ends in the owner-run hardware check. Reason: the real path cannot run in the Editor, `make unreal-smoke`, or automation (it needs the packaged app's Bluetooth identity), so nothing in-session could verify it. This replaces the earlier decision to wire both paths here.
- **UBT build strategy.** CMake stays the single build definition for the engine-independent modules. UBT links prebuilt arm64 static libraries built by CMake; no `.Build.cs` compiles those sources directly. This keeps the "builds and tests without Unreal" guarantee.
- **Self-contained app: try static first, Homebrew as the fallback.** The goal is a product with no Homebrew dylibs at runtime. `RowingContracts` links `protobuf::libprotobuf`, and the pinned Homebrew `protobuf 36.1` provides only dylibs (with abseil dylibs), so the milestone first tries to build protobuf and its abseil dependency statically from pinned sources under CMake for the app-bound libraries. This adds new pinned dependencies to `Config/BuildVersions.json` and `make doctor`. The sources are hash-verified downloads at configure time: CMake fetches the pinned release tarballs into `Build/` and checks a SHA-256 recorded in `BuildVersions.json`, so nothing is vendored and no new repo root is needed, at the cost of the first configure needing network access. Owner-confirmed fallback: if the static build fails, the milestone falls back to the Homebrew-based solution — `RowingContracts` keeps linking the pinned Homebrew protobuf/abseil dylibs, and the internal app runs in place on a machine that has them. In that case the spike records why the static build failed, the packaged-app consequence (the staged `.app` is not portable and has `/opt/homebrew` load commands) is documented in "Implementation notes", and making the package self-contained moves to build-order step 7 (unsigned ad-hoc build/package/verify). "Fails" means a concrete blocker recorded by the spike (build errors that a bounded effort does not resolve, or unresolvable symbol collisions with engine-bundled copies), not a preference. The separate stop-and-re-scope rule below still applies if static linking of the CMake libraries into UBT is unworkable as a whole.
- **HUD authoring.** Code-only: a C++ `UUserWidget` subclass. `Content/` stays `planned`, so there are no authored assets, no Git LFS use, and no Blueprint.
- **Device path.** Simulator only. `-SimulatorDevice[=<fixture>]` selects a `RowingSim` fixture as the machine. Launched without it, the app shows an idle "no device" HUD state and does not fall back to the simulator, so simulated data is never mistaken for a real device.
- **Journaling.** Owner-confirmed policy for the app overall: on by default for a real device, off for simulator runs, so simulator and automation runs never create a database or Keychain item. Since this milestone has no real-device path, the subsystem gives the session a no-op journal sink; the sealed journal in the app arrives with the real-device milestone under this same policy.
- **Simulator relocation.** The product app must not depend on `Tools/`, so `Tools/pm5-sim` (the mock machine, replay machine, and telemetry fixtures) moves to a product-owned engine-independent location, `Source/RowingSim`, and `-SimulatorDevice` links it in all configurations, gated by the launch flag.
- **View model location.** Snapshot-to-display formatting (time, pace/500 m, absent-value and gap state) is an engine-independent header inside `Source/WorkoutRuntime`, tested by CTest. The display model adds no new `Source/` root; the simulator relocation is the milestone's only new root, authorized here as `CLAUDE.md` requires. The Unreal widget binds already-formatted values.
- **Closing bar.** Milestone 5 closes when the automated checks pass: `make test`, `make format-check`, `make doctor`, `make unreal-smoke`, and and, if the static build succeeds, the `otool -L` self-containment check (under the Homebrew fallback the check is replaced by recording the Homebrew load commands). Seeing the HUD render and update in the packaged app, and running the Automation spec if a headless run is not possible in-session, stay flagged as outstanding and owner-run, like the real-PM5 runs in earlier milestones.
- **Order afterwards.** Which milestone follows (real-device integration, or route/boat/stroke animation) is deliberately left open and is decided when Milestone 5 closes, per just-in-time scoping.
- **After a session ends.** The HUD keeps showing the ended session's final snapshot with a visible Start New action. There is no auto-restart and no summary screen (Phase 2).
- **Latency instrumentation deferred.** The Phase 1 exit gate's "preliminary latency" evidence is not instrumented here; the owner deferred it to a later milestone or the gate run. Nothing in this milestone produces latency evidence, and the exit gate still needs it.
- **Engine configuration.** No engine or project ini changes. The HUD is created from module/subsystem code and the app uses the engine's built-in default map, so `Config/DefaultEngine.ini` (gitignored yet tracked) is left untouched and its status is not resolved here.
- **Real-device picker design, recorded for the follow-up.** The real adapter labels every candidate the same constant `DisplayLabel` ("Concept2 PM candidate", `Concept2PMDiscoveryMac.mm`) and `FRowingMachineId` is deliberately opaque, so candidates differ only by `SignalStrengthDbm`. Owner-confirmed: the follow-up's picker is a nearest-first list labelled by index and dBm (e.g. "PM5 #1 (-52 dBm)"), with no privacy change.
- **Owner-run.** `make unreal-shipping` and launching the packaged app stay owner-run and are not performed in-session.

## Implementation defaults settled during scoping (owner may veto)

These follow from reading the existing code and were not separately asked:

- **`FWorkoutSession` is one-shot.** A session that has Ended stays Ended (`Tick`/`Ingest` are no-ops, `End`/`Abort` return false). "Start New" constructs a fresh `FWorkoutSession`; the ended session's final snapshot is retained by the subsystem until the new session replaces it. `IRowingMachine` connection lifecycle stays with the subsystem, not the session.
- **Game-thread ticking and event draining.** `UWorkoutSubsystem` is a `UGameInstanceSubsystem`, which is not ticked by default; it ticks through `FTickableGameObject` (or an `FTSTicker` delegate) on the game thread. The subsystem, not the session, drains the machine every tick and forwards each event to the current session with `FWorkoutSession::Ingest`, then calls `Tick`, exactly as `pm5-tui` does. This is required, not a style choice: an Ended session's `Tick` returns before draining (`WorkoutSession.cpp`), so a session-owned drain would leave the machine's bounded event queue filling between sessions and on the ended-session screen, and the queue's overflow rule marks a session degraded. The subsystem also needs connection events itself for the disconnected banner. A new session built over an already-Ready machine reads the machine's connection state at construction, so Start New does not depend on seeing a fresh Ready event.
- **Monotonic timebase.** `Tick(NowMonotonicNs)` requires the same timebase as device event timestamps. The `Concept2PMMac` adapter stamps with `std::chrono::steady_clock` and `pm5-tui` ticks with it; `FMockRowingMachine` stamps from an injected clock. The subsystem uses `steady_clock` for both the ticks and the simulator's injected clock, so they are comparable.
- **HUD cadence.** The widget compares `FWorkoutSnapshot::Revision` and re-formats only when it changed, keeping the HUD update inside the 0.5 ms per-frame budget without invalidating layout each frame.
- **No invented values.** Absent metrics render as a fixed placeholder (`--`), never zero. During `bInputFrozen` the last device values remain visible but a disconnected banner is shown; the display model marks them stale, and nothing interpolates them. This mirrors "never synthesize distance after a gap or reconnect". The journal-health field is part of the display model, but the HUD shows the indicator only when a journal is attached (never in this milestone).
- **Simulator relocation is a pure move.** The ~1,600 lines under `Tools/pm5-sim` move to `Source/RowingSim` with no behavior change. To keep the diff mechanical, the `pm5_sim/` include prefix and the `pm5-sim` CMake target name are kept for this milestone; a rename to `RowingSim` is a separate follow-up. Its consumers (`pm5-tui`, `durability-spike`, `workout_runtime_tests`, and the `pm5_sim_*` contract/integration tests) are rewired to the new path only. `Tools/pm5-sim` is removed, and `CLAUDE.md`'s layout table and Diagnostics bullet are updated. `Source/RowingSim` depends only on `RowingCore`/`RowingDevice`.
- **Simulator in the app binary.** `-SimulatorDevice` requires `RowingSim` to be linked into the app in every configuration. Whether to compile it out of a released product is deferred to the packaged-product decision in a later milestone.
- **Public headers stay clean.** `Scripts/check_public_header_dependencies.py` continues to reject Apple or Unreal types in domain headers; Unreal-facing types live only under `Source/VirtualRowing`.
- **What links in this milestone.** `RowingCore`, `RowingDevice`, `RowingContracts`, `LocalData`, `WorkoutRuntime`, and `RowingSim`, plus static protobuf/abseil. `WorkoutRuntime` links `LocalData` (system SQLite) and, privately, `RowingContracts`, so those come along even though the app journals nothing yet. `LocalDataMac` (Swift CryptoKit shim, Keychain) and the `Concept2PM` CoreBluetooth adapter are not linked; their Swift-runtime, Keychain, adapter-copy, and Bluetooth-identity questions belong to the follow-up.

## Implementation notes (2026-09-19)

### UBT linkage spike outcome

The static build **succeeded**; the Homebrew fallback was not taken.

- **Mechanism.** `make native-app` (`Scripts/dev.py native_app`) configures a second CMake tree, `Build/native-app/`, with `CMAKE_BUILD_TYPE=Release`, `CMAKE_OSX_DEPLOYMENT_TARGET=14.0`, `VIR_STATIC_PROTOBUF=ON`, and `VIR_APP_LIBS_ONLY=ON` (no tests, no TUI, no `LocalDataMac`/`Concept2PM`). The existing Debug `Build/native/` tree is unchanged and keeps Homebrew protobuf, so the native test flow needs no network. CMake computes the static-archive closure of `WorkoutRuntime` and `pm5-sim` (including protobuf and abseil) and merges it with `libtool -static` into one `Build/native-app/lib/libVirRowingApp.a`, so `VirtualRowing.Build.cs` has a single `PublicAdditionalLibraries` entry. System SQLite is added with `PublicSystemLibraries`. `make unreal-smoke` runs `native-app` first and `VirtualRowing.Build.cs` throws a "run `make native-app`" error if the archive is missing.
- **Flags.** UBT compiles the module with `-std=c++20 -fexceptions -fno-rtti -O3` (Shipping) and targets `arm64-apple-macos14.00`; CMake uses C++20 and defaults, so the headers are includable as-is. Only domain headers are included from Unreal code (no protobuf header crosses the boundary), so the RTTI difference has no effect. The module sets `bEnableExceptions = true` explicitly. The deployment target is set to 14.0 so the archive's `minos` matches UBT's (verified with `vtool`).
- **Configuration.** The UBT-bound archive is Release, never the Debug tree's libraries. The Debug tree is not linked into UBT.
- **Static protobuf/abseil.** `Config/BuildVersions.json` now records `static_dependencies` (protobuf 36.1, matching the pinned `protoc`, and abseil 20250512.1, protobuf 36.1's own pin) with URLs and SHA-256 values. CMake `FetchContent` downloads and verifies them into `Build/native-app/_deps/` (first configure needs network; nothing is vendored). `make doctor` checks that the runtime pin equals the `protoc` pin and that each pin has a version, https URL, and SHA-256. The whole static build takes ~20 s. Homebrew's abseil 20260817.0 is not used.
- **Self-containment.** `otool -L` on the UBT-built Editor module `libUnrealEditor-VirtualRowing.dylib` shows no `/opt/homebrew` or `/usr/local` load command; SQLite binds to the system `/usr/lib/libsqlite3.dylib`. `make unreal-smoke` and `make unreal-package-verify` now fail on any Homebrew load command (`homebrew_load_commands` in `Scripts/dev.py`, covered by `test_unreal_packaging.py`).
- **Symbol collisions.** The engine bundles its own Protobuf (4.24) and abseil (20250127); the only editor image that exports them is `libUnrealEditor-NNEEditorOnnxTools.dylib`. To keep our copies out of the module's export table (so dyld cannot coalesce weak/inline symbols across images), the app tree builds with `-fvisibility=hidden -fvisibility-inlines-hidden`; the module dylib exports none of the protobuf, abseil, `FWorkoutSession`, or `pm5_sim` symbols (`nm -gU`). This engine install bundles no SQLite (no SQLite editor binary and no `ThirdParty/sqlite`), so there is no SQLite collision to manage; the module binds the system `libsqlite3.dylib`. The **Shipping (monolithic) link** — where engine and app static archives share one executable — is not checked in-session because building it is part of the owner-run `make unreal-shipping`; a duplicate-symbol link error there is the specific thing to look for, and would be fixed by hiding or renaming rather than dropping static linking.
- **UBT relink gotcha.** UBT does not treat a prebuilt archive as a link input, so a rebuilt archive alone leaves a stale module. `VirtualRowing.Build.cs` bakes the archive's timestamp into `VIR_NATIVE_ARCHIVE_STAMP`, so any archive change recompiles and relinks the module (verified: unchanged archive is "up to date", changed archive relinks).
- **Execution proof.** With a temporary `-NativeLinkageProbe` hook (kept, see below), a headless `UnrealEditor-Cmd` run executed a `FWorkoutSession` over a `FLocalDataJournalSink` on a temp SQLite file inside the Unreal process and returned `true`, exercising the linked WorkoutRuntime, LocalData/SQLite, protobuf wire mapping, and the simulator.

### What was built

- `Source/RowingSim` (moved with `git mv` from `Tools/pm5-sim`; `pm5_sim/` prefix and `pm5-sim` target unchanged) and `WorkoutDisplay.h` (`Source/WorkoutRuntime`; `FWorkoutDisplay`, `MakeWorkoutDisplay`, `MakeNoDeviceDisplay`, `FormatWorkoutElapsed`, `FormatWorkoutPace`) with `workout_display_tests` covering the seven named tests plus `workout_display_reflects_device_paused_and_resting`.
- `UWorkoutSubsystem`, `UWorkoutHudWidget`, and `FWorkoutSubsystemSpec` under `Source/VirtualRowing` (UCLASS headers live in `Private/`: `Public/` headers are scanned by `check_public_header_dependencies.py` as domain headers). `-SimulatorDevice[=<fixture>]` fixtures: `random30min` (default; varying rate, power, and pace) , `random10min`, `easy30s`, `sprint500m`, `race2000m`, `steady30min` (constant speed and rate, so pace and stroke rate never change), `intervals`, `abrupt_stop`, `packet_loss`, `no_rowing`, `device_completed`, `device_terminated`. The simulator's virtual time and the session's `Tick` timebase are one value, nanoseconds since the machine was (re)started, so they are comparable by construction. In simulator mode Start New rebuilds a rewound fixture machine, since a fixture is a fixed script.
- Display decisions the doc left open: distance is whole meters, pace is `M:SS` rounded to the nearest second (a device pace of zero or ≥100 min shows `--`), stroke rate is whole spm, heart rate zero counts as not supplied, watts is the stroke power when the device supplied it and otherwise the device average power (found during the first owner run: every `RowingSim` fixture reports only average power, so a stroke-power-only HUD showed `--`; a real PM5 reports both). Stale = link lost, `Stale`, or `Reconnecting`. Stale values are dimmed and the banner and connection label carry the state in text.
- HUD input: Only one action is enabled at a time (End Session while live, Start New once ended), so Tab has nowhere to move; the focused action is drawn with a bright fill so focus is visible. Escape never ends the session; it is handled by a Slate input pre-processor (registered while the HUD is constructed) rather than the widget, because Slate routes keys along the keyboard-focus path and the widget never sees Escape while the game viewport owns focus (found in the first owner run: focus cue and Escape did nothing). The initial focus is retried each frame until Slate reports it landed, since it cannot land before the widget is arranged; the outcome is written to `Logs/vir-startup-debug/trace.log` through `VirDebugLog`. It moves keyboard focus to the action that applies (End Session while rowing, Start New once ended), and Enter/Space on the focused button activates it. The HUD is created from `UWorkoutSubsystem::Tick` once a local player controller exists and is shown over the engine default map with no ini change and no `Content/`.
- `NativeLinkageProbe` (`-NativeLinkageProbe`) is kept because the app journals nothing yet, so without it nothing would pull `LocalData`/SQLite/protobuf into the module and their linkage would go unchecked, including in the owner-run Shipping link.

Code-review fixes (2026-09-19, after the owner runs): `UWorkoutSubsystem::Pump` bounds the simulator's virtual-time step to 1 s, so a pause, debugger break, or stall is skipped rather than replayed into the machine's bounded queue (which would have failed the machine permanently); a clock swap keeps virtual time continuous and a backwards clock never rewinds it (`survives a long stall without overflowing the machine queue` fails without the cap). `EnsureHud` no longer allocates a widget and resets the input mode every frame when `AddToViewport` adds nothing; it retries after 120 frames and replaces a widget that left the viewport. The display model shows a `WaitingToBegin` device as "Start rowing to begin" (Waiting phase) and a link lost before any sample as plain "Disconnected". `VirNativeLinkageProbe` catches every exception (returns `false`) and removes the database with its `-wal`/`-shm` sidecars only after the writer is closed. `make unreal-shipping` now runs `make native-app` first so a stale archive cannot be packaged.

## Findings deferred to the real-device milestone

A `/code-review high` pass over this milestone's branch (2026-09-19) also found defects in code delivered by earlier milestones. They are not introduced or worsened by Milestone 5 (the Unreal subsystem drains the machine itself and ingests every event, so it avoids the first), and they were not fixed here. Two of them matter for real-device journaling, so the follow-up milestone should scope them in:

- `WorkoutSession.cpp` (Milestone 4) — **`Ready` before `ConnectionRestored`.** The real `Concept2PM` adapter emits `ConnectionStateChanged(Ready)` before `FRowingConnectionRestored` (`FinishTelemetryIfReady` transitions, then emits). `OnConnectionState` restores the session on `Ready`, records the host-measured gap, and drops the later `Restored` event, so `LinkGapRecorded.device_reported` is effectively always false and `total_gap_ms` is host-measured. The mock machine emits `Restored` first, so no simulator test catches it; needs a test that uses the real adapter's order.
- `WorkoutSession.cpp` — **`CreateSession` is never retried.** `bPersisted` is set before the write, so a transient first-write failure leaves every later write pointing at a missing session row and loses the local workout even after the journal recovers.
- `LocalDataJournalSink.h` — **`WriteSummary` commit failure.** A commit that throws while SQLite keeps the transaction open leaves the writer's stage set, so later writes through the same sink fail; the runtime swallows the exception.
- `LocalDataJournalSink.cpp` — **summary revision is per sink, not per session** (`NextSummaryRevision`), so the second session's only summary is revision 2, and the revision is part of the sealed associated data.
- `Tools/pm5-tui/src/WorkoutJournalDriver.cpp` — **`Ingest()` and `Tick()` together.** `FWorkoutSession::Tick` also polls the machine, contradicting the "an ingesting caller must not let anything else poll" contract, so events can be drained before the TUI sees them; and **End Session mid-row** completes the session and immediately arms a new one, splitting one physical workout into two journal sessions (the second summary reports the PM5's cumulative distance and time, and the new session misses `CapabilityObserved`).

Not findings but noted: `WorkoutRuntime` gets no warning flags in `CMakeLists.txt`, and `docs/architecture/09-verification-strategy.md` still names `Tools/pm5-sim` (architecture text changes only through the normal path).

## Risks

- **UBT/CMake ABI and flag mismatches** (RTTI/exceptions, C++ standard, libc++ versions, Debug versus Release) — the reason the spike is first; if static linking proves unworkable the milestone stops and re-scopes with the owner rather than silently switching to compiling sources under UBT.
- **Building protobuf/abseil from pinned sources** adds pinned dependencies, a fetch or vendoring step (hash-verified), build time, and possible version skew between the `protoc` that generates code and the static runtime. Mitigated by one pinned version and a `make doctor` check; owner-confirmed, a failed static build falls back to the Homebrew dylibs (run-in-place, non-portable package) rather than blocking the milestone.
- **Third-party symbol collisions** (protobuf/abseil/SQLite versus engine-bundled libraries).
- **Simulator relocation churn.** Every consumer's include/link path changes at once; mitigated by keeping the include prefix and target name, by doing the move only after the spike succeeds, and by the existing `pm5_sim_*`, `workout_runtime_tests`, and `durability_spike_kill_recover` tests proving the move is behavior-neutral.
- **Built-in default map and code-created HUD.** Showing a widget with no authored map and no ini change is untested in this repository, including under a Shipping cook. If it does not work, the milestone stops and asks rather than adding `Content/` or ini changes silently.
- **Milestone size.** Spike, static protobuf, simulator relocation, subsystem, display model, and HUD are still substantial; the split of real-device work is the main bound, and the spike's outcome may justify a further split.
