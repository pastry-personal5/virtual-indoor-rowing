# Research: Concept2 Model D and PM5 integration

Research date: 2026-09-12  
Purpose: Establish the supported hardware boundary and current published communication surface.  
Authority: Point-in-time evidence only; the downloaded specification digest and hardware tests become implementation evidence.

## Executive findings

1. Software communicates with the Concept2 Performance Monitor, not the Model D mechanism. Model D units from October 2014 onward generally have PM5; older Model D units can be retrofitted. “Model D” alone is not a sufficient compatibility statement.
2. Concept2 encourages third-party PM5 apps and publishes a PM CSAFE Communication Definition. It recommends current PM5 firmware and warns the specification can change.
3. Concept2 labels its downloadable old Windows/macOS SDKs outdated and unsupported on the latest operating systems. The architecture should implement against the current published wire specification, not link the old macOS SDK.
4. The current communication definition covers USB, Bluetooth Smart, and RS485. PM5 supports Bluetooth; PM3/PM4 do not expose the same BLE product path.
5. BLE uses a Concept2 base UUID and services for device information, control/CSAFE, and rowing notifications. Published rowing notifications expose elapsed time, distance, workout/rowing/stroke state, drag factor, speed, pace, stroke rate, heart rate, power/interval/stroke values, optional force curve, logged-workout, battery/error data depending on firmware.
6. The status sample-rate characteristic supports 1 s, 500 ms default, 250 ms, and 100 ms. A 100 ms request is appropriate for responsive presentation when the actual device/firmware proves it stable.
7. The specification warns that public CSAFE and the full proprietary protocol should not be used simultaneously. BLE is documented as exposing the full proprietary path; the product must still use only documented, capability-gated operations and coordinate production questions with Concept2.
8. BLE measurement is not cryptographic hardware attestation. The published protocol gives data/state, not proof that an unmodified physical monitor or a particular human generated it.
9. Concept2 has an OAuth-based Online Logbook API, but PM telemetry and Logbook export are separate integration surfaces. A locally completed workout cannot depend on Logbook availability.

## Hardware/monitor boundary

Concept2's [PM5 support page](https://www.concept2.com/support/monitors/pm5) says PM5 is standard on Model D/Model E/Dynamic rowers from October 2014 onward and can be retrofitted to older indoor rowers. The [PM5 retrofit product](https://www.concept2.com/product/338) has Model D/E/Dynamic and Model D-specific mounting options.

Research implication: onboarding asks for monitor type, not just rower model. Launch requires PM5. Read and verify the connected erg machine type because PM5 firmware/configuration varies by rower/SkiErg/BikeErg and hardware generation.

Research implication: do not rely on the displayed revision string alone. Phase 0 downloads the source, records URL/access date/SHA-256, maps implemented fields to page/table, and diffs a newly downloaded digest during dependency review.

## Interfaces and protocol

The communication definition describes:

- PM3/PM4/PM5 USB device communication;
- PM4/PM5 RS485 for linked racing/multi-machine arrangements;
- PM5 Bluetooth Smart for applications;
- CSAFE framing transported differently on each link.

CSAFE standard frames use start/stop delimiters, byte stuffing for reserved bytes, and an XOR checksum. The published PM link limit is 120 bytes including delimiters/checksum/stuffing, while individual BLE characteristics impose smaller transaction constraints. Both layers need independent bounds/checks.

The specification states public and full proprietary CSAFE are alternatives rather than simultaneously mixed modes. Some non-BLE interfaces limit proprietary commands without Concept2 authentication. Bluetooth is shown with full proprietary access, but architecture should not infer permission for unpublished commands/material.

Research implication: use notifications for high-rate telemetry; serialize bounded CSAFE control transactions for managed workout configuration. Test response behavior on every supported PM tuple and require readback before Ready.

## BLE surface

Published base UUID: `CE06XXXX-43E5-11E4-916C-0800200C9A66`.

The PM Bluetooth profile describes the Concept2 base/discovery UUID as `CE060000-43E5-11E4-916C-0800200C9A66` for advertisement filtering. This is distinct from the post-connection `0x0030` rowing GATT service. Apple CoreBluetooth applies `scanForPeripheralsWithServices` to advertised service UUIDs, so filtering on `0x0030` can hide a PM5 that advertises the discovery UUID instead.

Relevant groups:

- `0x0010` device information with model, serial, hardware/firmware, manufacturer, erg machine type, and later MTU/DLE fields.
- `0x0020` PM control with command receive `0x0021` and response transmit `0x0022`.
- `0x0030` rowing service with notification characteristics.

The spec's table documents at least these data sources:

| ID | Key content |
|---|---|
| `0x0031` | elapsed time (0.01 s), distance (0.1 m), workout/interval/workout/rowing/stroke states, work distance/duration, drag factor |
| `0x0032` | speed (0.001 m/s), stroke rate, heart rate with 255 invalid, current/average pace, rest values, machine type |
| `0x0033` | interval count, average power/calories, split average/last split data |
| `0x0034` | status sample rate: 1 s, 500 ms, 250 ms, 100 ms |
| `0x0035` | stroke distance/timing, peak/average drive force, work/stroke, stroke count |
| `0x0036` | stroke power/calories/count and projected work |
| `0x0037`/`0x0038`/later additions | split/interval summaries |
| `0x003D` | multi-notification force curve on supported PM generations |
| `0x003E` | operational/verification/error/game/battery/watt-minute fields on listed firmware ranges |
| `0x003F` | logged-workout information |

Many entries list firmware-version-specific validity. Not every PM5 supports every later characteristic.

Research implication: capability discovery/profile controls required/optional subscriptions and exact allowed lengths. A parser checks length before access, decodes bytewise little-endian values, recognizes sentinels/unknown enums, and preserves provenance. Unknown firmware is not automatically allowed.

## Data authority

The PM directly supplies cumulative distance/elapsed time and stroke-derived performance values. Using PM distance as the official progress avoids integrating smoothed/rounded client speed and makes the session comparable with the monitor display.

Concept2's [PM5 connected-fitness article](https://www.concept2.com/blog/pm5-upgrade-or-retrofit-for-connected-fitness) emphasizes repeatable/comparable Performance Monitor data across eras. That supports making PM facts the measurement source, but it does not remove the need to detect transport gaps, reset, wrong machine type, or software emulation.

The Model D's damper is manual. No source reviewed exposed software-controlled mechanical resistance for this machine. Virtual slopes/wakes therefore cannot promise physical resistance changes.

## Firmware and connection UX

Concept2's [PM5 firmware/support guidance](https://www.concept2.com/support/monitors/pm5/firmware) and [How to use PM5](https://www.concept2.com/support/monitors/pm5/how-to-use) recommend current firmware. Exact latest versions differ by PM hardware and machine type, so a single numeric minimum is unsafe without the capability tuple.

EXR's current setup guidance tells users another app must not already be connected, but this is competitor documentation rather than the PM protocol authority. Treat exclusive-app behavior as an HIL/UX assumption: detect connection failure, instruct the user to close ErgData/other apps and reopen PM Connect, and do not auto-pair a different nearby PM.

## Security and fair-play limits

The reviewed BLE/CSAFE material defines transport, data, and some protocol authentication boundaries. It does not describe a client-verifiable signed metric stream, device certificate, or remote attestation.

Research implication: a malicious client or emulator can generate plausible payloads. Server validation, continuity, risk/evidence, supervised event controls, and careful UI labels are legitimate; “cheat-proof hardware verified” is not.

## Open questions for Concept2 / Phase 0

- Which PDF revision/digest is the intended current production specification, given its visible version inconsistencies?
- What production app identification/approval and trademark wording does Concept2 request?
- Are there supported recommendations for macOS CoreBluetooth connection parameters, subscription set, and 100 ms rate under busy 2.4 GHz conditions?
- Which PM5 hardware/firmware tuples are active in the target customer base, and what known notification layout/state issues exist?
- Is any special authentication/qualification expected for the exact managed-workout commands needed over BLE?
- Can a PM5 maintain simultaneous application and heart-rate connections as assumed, and what is the expected behavior when another phone/computer app is attached?
- What exact state/readback sequence does Concept2 recommend for synchronized online fixed-distance race setup and safe termination?
- What product evidence/approval is required before the Logbook marks a result verified or accepts richer split data?
